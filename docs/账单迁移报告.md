## 五、迁移中处理的关键问题

### 1. 两个未建模的枚举值（会导致迁移失败）

正式库出现了旧库没有的取值，Prisma 枚举必须补上，否则该行会被兜底成 `OTHER`/`PERSONAL` 造成**静默数据错误**：

- `accounts.kind = 'credit'`（信用卡）→ `BillAccountKind` 增加 `CREDIT`
- `books.kind = 'family'`（家庭账本）→ `BillBookKind` 增加 `FAMILY`

迁移已加白名单 + 未知值计数告警机制：本次**枚举值全部命中白名单，零兜底**。

### 2. 用户名字大小写不一致

源库是 `Leo`，目标库 seed 出来的是 `leo`。直接按 username 精确查找会**多建一个重名用户**。迁移脚本改为大小写不敏感匹配，正确复用同一个人。

### 3. `accounts.created_at` 字段缺失

源库后补的列（107 行中 104 行为 NULL），Prisma 模型补为 `DateTime?`，不做默认值以保持原样。

### 4. 时区存储语义（最容易踩的坑）

Prisma 的 `DateTime` 落到 PG 是 **`timestamp(3)`（无时区）**，与全项目 57 个 DateTime 字段的约定一致（**零处使用 `Timestamptz`**）。

- 源库 `occurred_at` 是本地时间 → 脚本按 `+08:00` 解释成瞬时 → 库里存 **UTC 墙钟**
  例：源 `2026-09-04 21:23:27` → 库里 `2026-09-04 13:23:27`（同一时刻）
- 回读时 Prisma 同样按 UTC 解释，**瞬时自洽**
- 写裸 SQL 校验时必须 `AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Shanghai'` 才能还原成本地时间字符串

### 5. 源库 id 不是从 1 开始

`transactions.id` 实际范围 **41,452 ~ 66,857**（历史数据整体导入过）。对账脚本原先按 `1..total` 取样本，取到 0 条 —— 已改为按真实 id 取首/中/末。

### 6. 自增序列

保留原 id 后必须 `setval`，否则下一条插入直接主键冲突。已对 6 张核心表执行并校验（`last_value == MAX(id)`）。

## 八、用户 ID 对齐（追加，务必先读）

### 8.1 契约

**门户 `user.id` ≡ 源库 `users.id`，代码里不做任何 id 映射表。**

账单 24,882 条流水的 `userId`、以及 accounts / categories / books / book_members / transfer_rules 等全部外键列都直接沿用源库 id。这样：
- `migrate-bills` 可以断言「门户已存在同 id 同名用户」，不一致就中止；
- bill 模块的权限判断（只看自己的数据）直接用 `session.user.id`，无需转换；
- 将来新增用户时两侧 id 语义天然一致。

⚠ 由于 `bill_*` 模型刻意不声明 `@relation`（保持模块解耦），**bill 表没有到 `user` 的外键约束** —— id 错位数据库不会报错，只能靠脚本断言守住。

### 8.2 改造前的实际差异

| 用户 | 源库 `users` | 改造前门户 `user` |
|---|---|---|
| Leo | id=**1**，ADMIN，hash `$2a$10$Wrkv…` | id=1 `leo`，ADMIN，hash `$2a$10$L/GG…`（**不同**） |
| liyanfei | id=**4**，MEMBER，hash `$2a$10$/cAG…` | id=**2**，MEMBER，hash 相同 |

即 liyanfei 两侧 id 不同（源 4 / 门户 2），且 Leo 的门户密码与账单密码不是同一个。两边密码哈希同为 bcrypt `$2a$10$` / 60 字符，**可逐位搬运**，Auth.js 的 `bcrypt.compare` 直接可用。

### 8.3 执行顺序（固定）

```
npx tsx scripts/migrate-users.ts     # 用户（按显式 id 写入，最先跑）
npx tsx scripts/migrate-bills.ts     # 账单（发现用户未对齐会中止）
npx tsx scripts/verify-bills.ts      # 对账
```

### 8.4 `migrate-users.ts`

- 按**显式 id** upsert（`create: { id, … }`），不让 PG 自增分配 id
- 自动处理「搬迁」：门户同名但 id 不同时，删旧行 → 按源 id 重建
- 改 id 前检查 `user_platform` / `todo` / `notify_channel` / `notify_log` 的引用行数，非空则中止
- 结束后 `setval('"user_id_seq"', MAX(id))`
- 参数：`--dry-run`、`--keep-password`（保留门户现有密码）、`--source <path>`

结果：门户 `id=1 Leo`(ADMIN) / `id=4 liyanfei`(MEMBER)，哈希与源库逐位一致，序列 = 4。

### 8.5 另一个坑：WAL 库无法只读打开

账单服务端**干净退出后 `-wal`/`-shm` 被合并删除**，此时 `sqlite3 -readonly` 直接报 `unable to open database file (14)`（同一文件用读写模式或 `file:?mode=ro` 都能打开）。

根因：SQLite **不允许在缺少 `-shm` 时只读打开 WAL 模式数据库**（只读连接不能创建 shm）。此前能跑通只是因为当时 `-wal`/`-shm` 还在。

**修法**：`migrate-bills.ts` 与 `verify-bills.ts` 统一先做**冷快照**（`ledger.db`，存在则连 `-wal`/`-shm` 一起拷到临时目录），之后所有查询都在快照上跑，并去掉 `-readonly`。这同时解决了「迁移/对账期间源库被写入、读到不一致中间状态」的隐患。
